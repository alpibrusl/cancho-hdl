Quick start

  
Two paths. The first needs no hardware; the second needs a Tang Nano 20K.

  

    
1. Check a contract no hardware


git clone https://github.com/alpibrusl/cancho-hdl.git
cd cancho-hdl
export CANCHO=<path-to-the-cancho-binary>
sh scripts/gate.sh     # about an hour; ends with GATE PASSED
# then, with the built chw:
chw check examples/uart-contract/uart.chw
chw generate examples/uart-contract/uart.chw \
    --target systemverilog

      
Needs the cancho compiler at the pinned revision. Python 3 is only the test oracle.

    
2. Run it on the board Tang Nano 20K


# OSS CAD Suite on PATH (yosys, nextpnr, openFPGALoader)
CANCHO=<compiler> sh scripts/build.sh chw
sh boards/tang-nano-20k/check.sh ./chw   # simulate first
DESIGN=stats CHW=./chw sh boards/tang-nano-20k/build.sh \
    boards/tang-nano-20k/build-stats --flash
cd boards/tang-nano-20k/host
cancho run labio.cho stats_test.cho --std

      
Loading needs raw USB access (sudo or a udev rule). DESIGN is leds, lab, stats, gemv, table, deadman, img or mem. Details: docs/fpga-experiments.md.

  

  
The host side is written in cancho: it opens the serial port through the Tty capability and nothing else, and cancho authority lists exactly that. Python appears only in tests and in two small helpers.

For humans

  
What this is, what you can do with it today, and how far to trust it.

  

    
What you can do

      
    
        
  • Describe registers, fields, interrupts and DMA layouts in one .chw file and have contradictions refused with a line, a column and a repair.
    • 
        
  • Generate the SystemVerilog register block, the C header, the device tree, a cancho binding and CMSIS-SVD from it.
    • 
        
  • Ask which generated files a change makes stale before you touch the driver (impact).
    • 
        
  • Put the register block on a Tang Nano 20K behind a serial port and drive it from cancho.
    • 
        
  • Start from a gallery example and change the contract, not the glue.
    • 
      

    
How far to trust it

      
    
        
  • The checker and parser agree with the Python reference on tens of thousands of mutated inputs, with every difference listed.
    • 
        
  • The board results are compared byte for byte with software, and a seeded bug makes the comparison fail.
    • 
        
  • Timing, area and vendor IP are never labelled verified, and a skipped check is never a pass.
    • 
        
  • The board glue (UART bridge, the designs) is hand-written and not part of the product. Nothing has moved a servo.
    • 
      

  

  
A contract is plain JSON or the textual form, so it can be diffed and hashed. This is the whole contract for the board's LEDs; the two registers become the register block, a header and the rest.


{ "version": "0.1.0",
  "block": { "name": "TangLeds", "base_address": "0x40000000", "bus_width": 32, "endianness": "little",
    "registers": [
      { "name": "LEDS",    "offset": "0x00", "kind": "RW", "reset": "0x00000000",
        "fields": [ { "name": "ON", "lsb": 0, "msb": 5 } ] },
      { "name": "SCRATCH", "offset": "0x04", "kind": "RW", "reset": "0x00000000",
        "fields": [ { "name": "VALUE", "lsb": 0, "msb": 31 } ] } ] } }






  
Stop maintaining five copies

  
When a field widens, the driver is wrong silently. When an interrupt link breaks, the device tree is wrong silently. Here the failure is loud and structured.

  

    
📄
One source
Registers, fields, interrupts and DMA layouts in one contract. Generators are deterministic, so a diff of a generated file is meaningful.

    
🚫
Refusals are data
Overlaps, bad alignment, unresolved interrupts and ownership errors come back as codes an agent can match on.

    
🎯
Impact analysis
diff and impact list which generated artifacts a change invalidates, decided by byte-comparing generator output.

    
🧾
No over-claiming
A report counts only what ran. A skipped roundtrip is never a pass, and vendor tools stay trust boundaries.

  






  
Five targets from one contract

  
Consumers never need to know cancho-hdl exists.

  

    
C header
Structs and volatile accessors. Compiles clean under gcc and clang.

Typed driver-side declarations.

    
Device tree
A reg and interrupts fragment.

    
SystemVerilog
The register file, structurally checked.

    
CMSIS-SVD
XML validated against the SVD schema.

What is not claimed

  
Written down so a report cannot imply it.

  

    
Not working hardware
Timing, area and vendor IP are trust boundaries, never labelled verified.

    
No SystemVerilog behaviour check yet
That needs Verilator or cocotb. Only structure is checked today.

    
Mostly still Python
The textual parser, the JSON loader, the schema validator, the semantic checker and the conformance run are ported. The generators, diff and report remain the Python reference, being replaced.

Everything an agent needs is checked, tagged or hashed. No key, no model, no network after the clone.

What not to get wrong

      
    
        
  • Do not fix a refusal by editing the fixture or the expected sidecar. Fix the contract.
    • 
        
  • Do not hand-edit a generated file. Change the .chw and generate again; the two SystemVerilog generators must stay byte-identical.
    • 
        
  • Python is allowed only under oracle/ and tests/. The Python line ceiling only goes down.
    • 
        
  • Board results are SRAM-only and judged against the same computation in cancho. A skipped step is not a pass.
    • 
        
  • Nothing here has moved a servo, and no speed advantage is claimed. Do not add either to a report.
    • 
        
  • Loading a bitstream needs sudo or a udev rule. Do not run it unasked.
    •

Ask your coding agent to try it

  
Paste this into Claude Code, Codex or any coding agent that can run commands. It installs the pinned compiler, proves the install with both gates (no network, no key, no model), and runs the tool on the examples.

  

    
prompt raw

    
Install cancho-hdl and check it on this machine. Work in a new empty directory, keep every path free of spaces, and never use sudo. Run steps 2 to 5 in one shell session. Report honestly; do not retry a failing command in a loop and do not edit the repository to make a command pass.

1. Check that `git`, `cargo` (Rust, via rustup), a C compiler (`cc`), `clang`, `gcc`, `python3` with `pip`, and `sh` exist. If one is missing, stop and tell me which; do not install system packages on your own.

2. Get the two repositories side by side, both cloned into the new empty directory (call it the parent):
   git clone https://github.com/alpibrusl/cancho-hdl.git
   git clone https://github.com/alpibrusl/cancho.git
   git -C cancho checkout "$(cat cancho-hdl/.cancho-rev)"

3. Build the compiler (a few minutes) and point at it. Install the Python oracle's two packages at the pinned version (Python is only the test oracle, not part of the product):
   (cd cancho && cargo build --release -p cancho)
   export CANCHO="$PWD/cancho/target/release/cancho"
   pip install jsonschema==4.26.0 lxml

4. Prove the install works. This needs no network, no key and no model. It takes about an hour (measured 3,629 s with a second gate running on the same machine; not measured alone):
   cd cancho-hdl
   sh scripts/gate.sh ; echo "exit $?"     # must end with: ######## GATE PASSED, then exit 0

5. Use the cancho tool `chw` on the examples (the gate built it at /tmp/chw):
   /tmp/chw validate examples/uart-contract/uart.chw ; echo "exit $?"            # expect exit 0
   /tmp/chw validate examples/refusal/bus-width-invalid.chw ; echo "exit $?"     # expect schema-invalid at a line:column, exit 1
   /tmp/chw parse examples/refusal/parse-error.chw ; echo "exit $?"              # expect parse-error at 2:26, exit 1
   /tmp/chw conform .                                                            # the refusal fixtures, a table
   /tmp/chw impact examples/uart-contract/uart.chw tests/diff/fixtures/uart_rebase.chw --pretty
   The last command lists which generated artifacts a register-map change makes stale.

6. Tell me, briefly:
   - whether the gate exited 0 and whether `gate.sh` ended with GATE PASSED;
   - the first line each command printed in step 5, with its exit code, and the last line of `chw conform`;
   - which targets `impact` marked stale;
   - anything that failed, with the exact error.
Not claimed: that generated hardware works, timing, or a SystemVerilog behavioural check. Docs: README.md, docs/cancho-port.md (what is ported and what is still Python), docs/guarantees.md.

  

  
It needs no key and no model, and takes about an hour (mostly the gate; the compiler build is a few minutes). The same text is in docs/agent-prompt.md, and a Claude Code skill for checking contracts and reading impact reports is in skills/cancho-hdl.

  

    
prompt: the board raw

    
Check cancho-hdl on a Tang Nano 20K attached to this machine. Work in a new empty directory, keep every path free of spaces. Do not use sudo: if loading the bitstream needs it, stop and tell me the exact command. Report honestly; do not retry a failing command in a loop and do not edit the repository to make a command pass.

1. Check that `git`, `yosys`, `nextpnr-himbaechel`, `gowin_pack`, `openFPGALoader` and `iverilog` are on PATH (the YosysHQ OSS CAD Suite has all of them) and that `lsusb` lists `0403:6010`. If one is missing, stop and tell me which; do not install system packages on your own.

2. Clone the repositories side by side and use the branch that has the board work:
   git clone https://github.com/alpibrusl/cancho-hdl.git
   git clone https://github.com/alpibrusl/cancho.git
   Build the cancho compiler as cancho/README says, and build `chw` with `sh scripts/build.sh chw`.

3. Prove the designs in simulation first (no board needed): `sh boards/tang-nano-20k/check.sh`. Every line ending in `RESULT:` must say `0 failed`, and Yosys must print no warning.

4. Build and load one design, for example the table query, then run its host test written in cancho (loading is the step that needs raw USB access, so ask me before running it):
   DESIGN=table CHW=./chw sh boards/tang-nano-20k/build.sh boards/tang-nano-20k/build-table --flash
   cd boards/tang-nano-20k/host && cancho run labio.cho table_test.cho --std

5. Tell me, briefly: the last line of `check.sh`; for the board test, the lines `figures different ... : N` (want 0); anything that failed, with the exact error.
Not claimed: any speed advantage, that a servo moved, or timing against an outside reference. Docs: docs/fpga-experiments.md, docs/tang-nano-20k.md.
