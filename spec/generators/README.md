# Generators

> **Status: Phase 0.** Five generators are committed to as the
> MVP set. This page names each, fixes the contract of its
> output, and lists the open questions for Phase 1.

The five targets are taken from parent proposal §5.3. Each is
a **deterministic function** from the contract IR (see
[`spec/contract-schema/README.md`](../contract-schema/README.md))
to a text artifact. Given the same IR, the generator produces
byte-identical output; given a structurally different IR, the
generator produces structurally different output.

The bus protocol for the SystemVerilog generator is **AXI4-Lite**
(memory-mapped slave). This is the only protocol Phase 1
targets. Multi-protocol support is out of scope per parent
proposal §8.3.

---

## 1. The contract every generator honours

Every generator, regardless of target:

1. **Reads the contract IR only.** It does not parse source
   `.chw` text, does not consult a database, does not call out
   to the network.
2. **Produces deterministic output.** Two runs over the same
   IR yield byte-identical files. This is checked by the
   roundtrip suite under `tests/roundtrip/`.
3. **Emits the stable ID of every entity it touches.** A
   generated header that defines `UART_CTRL_BAUD_DIV_Msk`
   contains a comment with the ID
   `chw:UartRegs.register.CTRL.field.BAUD_DIV`. This is the
   one link from generated code back to the contract.
4. **Refuses on missing features**, never silently degrades.
   Asking for `c-header` on a `.chw` that uses an unimplemented
   feature is `generator-unimplemented`, not a partial file.
5. **Fails the run, not just the artifact**, on its own error.
   A malformed IR the checker should have caught is refused
   with `internal` (`tier: Unknown`).

## 2. `c-header` — C `struct` + `volatile` accessors

**Phase:** Phase 1 — **landed.**
**Audience:** C drivers, firmware.
**Output:** A single `.h` file with one `typedef struct` per
register block, plus per-register bitfield typedefs.

### 2.1 Output contract

```c
/* Generated by cancho-hdl from <source>. Do not edit. */
#ifndef CANCHO_HDL_<GUARD_BLOCK_NAME>_H
#define CANCHO_HDL_<GUARD_BLOCK_NAME>_H

#include <stdint.h>

/* chw:<block>.register.<reg>.field.<f> */
typedef struct {
    uint32_t ENABLE   : 1;
    uint32_t PARITY   : 2;
    uint32_t _rsvd    : 3;
    uint32_t BAUD_DIV : 8;
    uint32_t _word16  : 16;
} ctrl_t;
/* chw:<block>.register.CTRL */

typedef struct {
    volatile uint32_t CTRL;
    volatile uint32_t STATUS;
    /* ... one entry per register, in offset order ... */
} UartRegs_t;

#define UARTREGS_BASE 0x40000000u

#endif
```

### 2.2 Stable guarantees

- The header compiles under `clang-19` and `gcc-14` with
  `-Wall -Wextra -Werror -std=c11`. Verified in
  `tests/roundtrip/c_header_compiles.rs`.
- Field layout matches the contract bit ranges. The
  roundtrip test reads each generated register, sets a value
  through the binding, and reads it back through a mock bus.
- Reserved bits are emitted as `_rsvd` (within a bitfield) or
  `_word<N>` (spanning more than one field), so accidental
  access is visually obvious.
- A `RO` register has `const volatile`; a `WO` register has a
  write-only marker; `RW` is plain `volatile`. `W1C` / `W0C`
  / `W1S` / `W0S` get a comment naming the access semantic;
  the C type stays `volatile uint32_t`.
- Reset values are emitted as `#define UARTREGS_CTRL_RESET
  0x00000000u` so a driver can initialise from them.

### 2.3 Non-guarantees

- The header does not encode `RC` (read-to-clear) as anything
  special. A driver that reads a `RC` field is responsible for
  knowing the read clears it. The contract notes this in a
  comment.
- The header does not provide interrupt helpers. Those come
  from the `cancho-binding` target.

## 3. `cancho-binding` — Cancho driver-side declarations

> **Status: Phase 2 — landed.** Implemented at
> `oracle/legacy/gen/cancho-binding/cancho_binding.py`; pinned by
> `tests/roundtrip/cancho_binding_validates.py`.

**Phase:** Phase 2.
**Audience:** Cancho Core programs that drive the peripheral.
**Output:** A single `.cancho` file with typed declarations
matching the contract.

### 3.1 Output contract

```cancho
// Generated by cancho-hdl from <source>. Do not edit.

module uart_regs {
    foreign block UartRegs @ 0x40000000 : u32;

    // chw:UartRegs.register.CTRL.field.ENABLE
    fn ctrl_enable() -> bool;
    fn ctrl_enable_set(v: bool);

    // chw:UartRegs.register.CTRL.field.PARITY
    fn ctrl_parity_get() -> Parity;
    fn ctrl_parity_set(v: Parity);

    // chw:UartRegs.interrupt.rx_ready
    capability UartRegsRxReady
    fn rx_ready_arm();
    fn rx_ready_status() -> bool;
    fn rx_ready_clear();
}

enum Parity { None, Even, Odd }
```

A block with `dma_buffers` also gets one `buffer` declaration
per buffer. Fields carry the c-header's size convention and the
§3.2 ownership rule (a CPU-owned field gets getter + setter; a
DEVICE-owned field gets the getter only, with the no-setter
line — the type system is the enforcement).

(Names uniformly register-prefixed; the bare `parity_*` in the
Phase 0 sketch was a hand-written abbreviation — see §3.2 for
the landed palette.)

### 3.2 Stable guarantees

- Every accessor carries a comment with the stable ID of the
  entity it touches, matching §1 rule 3.
- `DEVICE`-owned DMA fields have no setter; the type system
  is what enforces this — there is no runtime check to add.

The landed palette (the sketch's open points, resolved and
pinned by the roundtrip suite):

- **Accessor names are uniformly register-prefixed**
  (`ctrl_enable`, `parity_set` becomes
  `ctrl_parity_get/ctrl_parity_set`). The sketch's bare
  `parity_*` was a hand-written abbreviation; two registers can
  legitimately declare same-named fields, so the prefix is
  load-bearing.
- **Getters**: bare name for `bool` (`fn ctrl_enable() -> bool;`),
  `_get()` for typed values (`fn ctrl_parity_get() -> Parity;`).
- **Register kind → available accessors**: `RW` get+set; `RO`,
  `RC` get only; `WO`, `W1S`, `W0S` set only; `W1C`, `W0C`
  `_clear()`.
- **Types**: 1-bit fields → `bool`; enum fields → a
  module-level `enum <PascalField>` (labels verbatim); other
  fields → `u32` (the bus-width grain).
- **Capability name** is `Pascal(block) + Pascal(interrupt)`
  (`UartRegsRxReady`; the sketch's `UartRxReady` was a
  hand-written shortening). §3.3's rule stands: users may
  rename capabilities; the diff tool continues to match by
  stable ID.
- **DMA buffer fields** carry the c-header's size convention
  (explicit `size`, else 4 — the packed-struct grain both
  artifacts share), mapped to `u8`/`u16`/`u32`/`u64`. Any
  other declared size refuses as `generator-unimplemented` —
  and the c-header now refuses that same input, so the two
  artifacts cannot disagree silently.
- **The parse claim**: no cancho Core toolchain exists in this
  environment, so "parses under cancho Core" is checked
  structurally (the landed test pins line shapes, not a
  compiler); a real parse is the same upgrade path the
  systemverilog target has with iverilog.
- **Byte-identity pattern worth noting**: the binding encodes
  names, widths, kinds, and linkage — not offsets. A pure
  register rebase leaves the file byte-identical, which the
  impact tool proves (`stale: false` with the byte-identical
  reason; see spec/diagnostics README §7.1).

### 3.3 Non-guarantees

- The binding does not generate driver logic. It exposes
  accessors only.
- Capability names follow the convention `<Block>Upper(interrupt
  name)`; users may rename them, but the diff tool continues to
  match by stable ID.

## 4. `devicetree` — DTSI fragment

> **Status: Phase 2 — landed.** Implemented at
> `oracle/legacy/gen/devicetree/devicetree.py`; pinned by
> `tests/roundtrip/devicetree_generates.py`.

**Phase:** Phase 2.
**Audience:** Linux / Zephyr / RTOS device-tree consumers.
**Output:** A `.dtsi` fragment describing the block.

### 4.1 Output contract

```devicetree
/* Generated by cancho-hdl from <source>. Do not edit. */
&soc {
    uart_regs: uart_regs@40000000 {
        /* chw:UartRegs */
        compatible = "cancho,uart-regs-v0";
        reg = <0x40000000 0x14>;
        interrupt-parent = <&intc>;
        interrupts = <5 4>; /* chw:UartRegs.interrupt.rx_ready, IRQ 5 */
        #address-cells = <1>;
        #size-cells = <1>;
        bus-width = <32>;
    };
};
```

The landed details the sketch left open:

- **Node name and label** are the snake-cased block name
  (`UartRegs` → `uart_regs`) — the sketch's shorthand `uart`
  label is hand-written prose; the generator is deterministic,
  so both slots come from the same name. The unit address is
  the base address in hex without `0x` (DTS unit-address rule).
- **`compatible`** is hyphenated (`cancho,uart-regs-v0` —
  DTS-compatible-string convention, unlike the node name).
- **`reg`** is `<base size>` with the §4.2 formula
  (`max_offset + bus_width/8`; the sketch's example size was
  illustrative). A base beyond one 32-bit address cell is
  refused (`generator-unimplemented`), never widened.
- **`interrupts`** carries one flag cell per the sketch; the
  flag value is the sketch's placeholder — the real encoding
  belongs to the board's `intc` binding.
- **`input`-like properties**: none — the fragment is
  block-level only (§4.3).

### 4.2 Stable guarantees

- `reg` is the block's address range, computed from the
  highest register offset and the block's bus width.
- `interrupts` lists every interrupt `number` in declaration
  order, with the stable ID as a comment; a block with no
  interrupts emits no interrupt-parent/interrupts lines.
- Determinism: two runs over the same IR are byte-identical,
  pinned by the roundtrip suite. When `dtc` is on `$PATH`, each
  fragment is additionally parsed through it (upstream DTS
  schema check, spec §4.2's `devicetree_validates` lane).

### 4.3 Non-guarantees

- The fragment does not encode clocks, resets, or pinctrl.
  Those are out of contract scope and added by the board-level
  DTS, not the generator.
- The interrupt flag cell is the sketch's placeholder, not a
  semantic encoding — which IRQ type/level applies is decided
  by the board's `interrupt-parent` binding (Trust lane).
- DMA buffers have no representation in this fragment.

## 5. `systemverilog` — Register RTL module

**Phase:** Phase 1 — **landed (structural).**
**Audience:** FPGA / ASIC integrators, simulator testbenches.
**Output:** A single `.sv` file implementing the AXI4-Lite
slave that decodes the register map.

### 5.1 Output contract

```systemverilog
// Generated by cancho-hdl from <source>. Do not edit.
// chw:UartRegs
module uart_regs_axi #(
    parameter ADDR_WIDTH = 32,
    parameter DATA_WIDTH = 32
) (
    input  wire                    clk,
    input  wire                    rst_n,

    // AXI4-Lite slave
    input  wire [ADDR_WIDTH-1:0]   s_axi_awaddr,
    input  wire                    s_axi_awvalid,
    output wire                    s_axi_awready,
    /* ... full AXI4-Lite port list ... */

    // Decoded register-side outputs
    output wire [31:0]             reg_ctrl_out,
    output wire [31:0]             reg_status_out,
    /* ... one port per register ... */
);

    // chw:UartRegs.register.CTRL
    reg [31:0] r_ctrl;
    assign reg_ctrl_out = r_ctrl;

    // chw:UartRegs.register.STATUS
    reg [31:0] r_status;
    assign reg_status_out = r_status;

    // Write decoding, read mux, AXI4-Lite handshake...
endmodule
```

### 5.2 Stable guarantees

- The module parses under Yosys (`read_verilog`) and slang
  (`slang --parse`). Verified in
  `tests/roundtrip/systemverilog_parses.rs`.
- The decode logic matches the contract: every register at
  `offset` is read/written through the corresponding port,
  every field's bit range is honoured, every enum value is
  defined as a `localparam`.
- Reset values are applied in the system signal, with a comment
  per register naming the reset value from the contract.
- The module does not implement the **behavior** of the
  registers. `CTRL.ENABLE` exposes the bit; it does not start
  a baud-rate generator. That is what users wire up
  externally.

### 5.3 Non-guarantees

- Functional correctness of the register module beyond the
  decode. Tier `Trust`. The user wires the decoded ports to
  whatever behavior they want; cancho-hdl does not claim the
  wires do the right thing.
- That the generated module meets timing, area, or power.
  Tier `Trust`. Vendor toolchain.

## 6. `svd` — CMSIS-SVD XML

**Phase:** Phase 2 — **landed.**
**Audience:** ARM CMSIS tools (cortex-debug, svd2rust,
keil-mdk).
**Output:** A single `.svd` file in CMSIS-SVD XML format.

Three decisions fixed at implementation time (they pin the
bytes, so they are recorded here, not invented silently):

- **The peripheral `<name>` is the block name verbatim.**
  The IR has no short-name field; the generator does not invent
  one (`UartRegs` stays `UartRegs`). The sketch's `UART` below
  was illustrative. The `chw:` stable-ID comment carries the
  trace.
- **Enum fields emit `<enumeratedValues>`** (in declaration
  order, `name`/`value` pairs) — the SVD-native representation
  of what the IR carries.
- **Full SVD-native access mapping** (§6.1 table): the same
  write/read semantics the reference simulator enforces,
  expressed so CMSIS tools understand them natively.

### 6.1 Output contract

```xml
<?xml version="1.0" encoding="utf-8"?>
<!-- Generated by cancho-hdl from <source>. Do not edit. -->
<device schemaVersion="1.0" xmlns:xs="http://www.w3.org/2001/XMLSchema-instance" xs:noNamespaceSchemaLocation="CMSIS-SVD.xsd">
  <!-- chw:UartRegs -->
  <name>UartRegs</name>
  <version>0.1.0</version>
  <addressUnitBits>8</addressUnitBits>
  <width>32</width>
  <peripherals>
    <peripheral>
      <!-- chw:UartRegs -->
      <name>UartRegs</name>
      <baseAddress>0x40000000</baseAddress>
      <size>32</size>
      <registers>
        <register>
          <name>CTRL</name>                                            <!-- chw:UartRegs.register.CTRL -->
          <addressOffset>0x0</addressOffset>
          <access>read-write</access>                                  <!-- per the map below; precedes resetValue (XSD order) -->
          <resetValue>0x00000000</resetValue>
          <fields>
            <field>
              <name>ENABLE</name>                                      <!-- chw:UartRegs.register.CTRL.field.ENABLE -->
              <lsb>0</lsb><msb>0</msb><access>read-write</access>
            </field>
            <field>
              <name>PARITY</name>                                      <!-- enum fields add enumeratedValues -->
              <lsb>1</lsb><msb>2</msb><access>read-write</access>
              <enumeratedValues>
                <enumeratedValue><name>None</name><value>0</value></enumeratedValue>
                <enumeratedValue><name>Even</name><value>1</value></enumeratedValue>
                <enumeratedValue><name>Odd</name><value>2</value></enumeratedValue>
              </enumeratedValues>
            </field>
            <!-- ... -->
          </fields>
        </register>
        <!-- ... -->
      </registers>
    </peripheral>
  </peripherals>
</device>
```

The access map (register-level; fields carry the plain
`<access>` value):

| Contract kind | SVD `<access>` | Additional element |
|---|---|---|
| `RO` | `read-only` | — |
| `WO` | `write-only` | — |
| `RW` | `read-write` | — |
| `RC` | `read-write` | `<readAction>clear</readAction>` |
| `W1C` | `read-write` | `<modifiedWriteValues>oneToClear</modifiedWriteValues>` |
| `W0C` | `read-write` | `<modifiedWriteValues>zeroToClear</modifiedWriteValues>` |
| `W1S` | `read-write` | `<modifiedWriteValues>oneToSet</modifiedWriteValues>` |
| `W0S` | `read-write` | `<modifiedWriteValues>zeroToSet</modifiedWriteValues>` |

Element order follows the CMSIS-SVD `registerType` sequence:
`access` and `resetValue` live inside the
`registerPropertiesGroup` (`access` before `resetValue`),
`modifiedWriteValues` / `readAction` follow the group. An
earlier sketch emitted `resetValue` before `access`; the XSD
rejects that order, so the sketch above is corrected.

### 6.2 Stable guarantees

- The file validates against the CMSIS-SVD XSD bundled with
  this repo (`spec/generators/CMSIS-SVD.xsd`, schema 1.3,
  copyright ARM Limited, vendored with its license header and
  named in NOTICE). Verified in
  `tests/roundtrip/svd_validates.py` when lxml is available
  (structural checks run everywhere).
- Every entity carries an XML comment with its stable ID,
  matching §1 rule 3.
- Reset values are emitted as `<resetValue>` even when the
  contract marks them undefined; an undefined reset becomes
  `<resetValue>0x0</resetValue>` plus a comment naming the
  absence.
- DMA buffers are not register-map content: they are named by
  stable-ID comments, like interrupts.

### 6.3 Non-guarantees

- The SVD does not include interrupt `<interrupt>` elements;
  CMSIS-SVD interrupts are board-level. The generator emits a
  comment naming each interrupt by ID instead.
- That CMSIS tools interpret `modifiedWriteValues` /
  `readAction` / `enumeratedValues` the way the contract's
  reference simulator does — the mapping is emitted, applied
  by third-party tooling, and outside cancho-hdl's checking
  reach.

## 8. Open questions for Phase 1

1. **Multi-target builds.** Phase 1 ships one target per
   `generate` invocation. Phase 2 should answer whether
   `generate --all` is a separate command or a flag, and
   whether the output directory layout is fixed or
   user-configurable.
2. **Template vs. string-built.** Phase 1 should commit to
   either templating (Handlebars / Tera / Askama) or direct
   string building. The `c-header` and `systemverilog`
   generators are small enough that direct string building is
   the simpler choice; the choice is recorded here as Phase 1
   work, not decided in Phase 0.
3. **CMSIS-SVD XSD vendoring.** The XSD lives upstream. Phase
   2 must either vendor it under `spec/generators/` or
   document a pinned URL and accept the network dependency
   for tests. Vendoring is the safer default.
